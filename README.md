# EasyRead Prototype

A prototype application developed by the UNICEF Office of Innovation’s Ventures – Frontier Tech Team to explore the use of Large Language Models (LLMs) in converting complex documents into accessible “Easy Read” formats with simplified text and relevant images. This prototype investigates the potential and infrastructure needed to support automated Easy Read content generation and is intended solely for research and experimentation, not as an implementation of formal Easy Read guidelines.

## Disclaimer

**This prototype was created for evaluation purposes only.**

This repository contains an experimental prototype. It is designed for exploration and learning purposes only. It is not intended for use in UNICEF programs or by program partners without further validation and testing. The code and applications in this repository are **not** production-ready and should not be deployed in any real-world use case without further hardening. The content generated by this application uses Artificial Intelligence and will contain errors, inaccuracies, or biases.

## Overview

EasyRead uses Large Language Models (LLMs) to process complex content, generate simplified content, and match sentences with appropriate images through vector similarity search. It applies a four-step process:

1. Create a set of Easy Read sentences and accompanying image descriptors.
2. Review the output, flagging missing and inconsistent content.
3. Use the revision to generate a new set of sentences and image descriptors.
4. Use the image descriptors to match stored images using embedding similarity.

## Key Features

- PDF to accessible format conversion using AI
- Automated image selection from symbol libraries
- Content revision and editing capabilities
- DOCX export

## Technology Stack

- **Backend**: Django REST API, PostgreSQL with `pgvector`
- **Frontend**: React + Vite, Material UI
- **AI Services**: AWS Bedrock for embeddings, plus model providers configured through the application flow
- **Deployment**: Docker Compose + Nginx (local and evaluator deployment examples)

## Quick Start

EasyRead can be run in two ways:

- **Local Python + Node**: best for development and debugging.
- **Docker Compose**: best for a reproducible local or evaluator environment.

### Prerequisites

- Python `3.11+`
- Node.js `18+`
- PostgreSQL `15+` with the `pgvector` extension installed and enabled
- Working API credentials for the features you plan to use
  - **Required for image imports and embedding-based image matching in the current repo configuration**: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_REGION_NAME`

## Local Python Setup

### 1. Create the root environment file

EasyRead loads configuration from the repository root `.env` file.

```bash
cp .env.example .env
```

Update `.env` with at least:

- `SECRET_KEY`
- `DB_ENGINE`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`
- `DJANGO_HOST`, `DJANGO_PORT`
- `VITE_HOST`, `VITE_PORT`, `VITE_API_BASE_URL`, `VITE_MEDIA_BASE_URL`
- AWS credentials for Bedrock if you want to import or use symbol matching

Important notes:

- If `DATABASE_URL` is set, it overrides the individual `DB_*` settings.
- The frontend must point to the same backend port you start Django on.

### 2. Create a PostgreSQL database with `pgvector`

Use your local Postgres workflow, but make sure the `vector` extension exists in the target database.

Example:

```sql
CREATE USER easyread_user WITH PASSWORD 'easyread_password';
CREATE DATABASE easyread OWNER easyread_user;
\connect easyread
CREATE EXTENSION IF NOT EXISTS vector;
```

If migrations fail with `type "vector" does not exist`, the extension has not been installed in the database you are actually using.

### 3. Start the backend

```bash
cd backend
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py validate_api_keys --test-embedding
python manage.py start_server
```

`start_server` reads `DJANGO_HOST` and `DJANGO_PORT` from `.env`.

### 4. Start the frontend

```bash
cd frontend
npm install
npm run dev
```

By default, Vite reads `VITE_HOST` and `VITE_PORT` from the root `.env` file.

### 5. Open the app

Typical local URLs are:

- Frontend: `http://127.0.0.1:5173/`
- Backend API: `http://127.0.0.1:8000/api/health/`

Adjust those if your `.env` uses different ports.

## Populate Symbol Libraries

The UI does not ship with image sets already loaded in the database. To make symbol collections available in the app, import them after the backend is running and migrations are complete.

### Bulk import a folder of symbols

```bash
cd backend
source venv/bin/activate
python manage.py bulk_upload_images /path/to/symbols --use-folder-names --skip-existing
```

Useful options:

- `--use-folder-names`: turns the top-level folder names into image set names
- `--skip-existing`: avoids duplicating previously imported images
- `--dry-run`: previews what will be imported without writing to the database

Recommended folder layout:

```text
/path/to/symbols/
  ARASAAC/
  PiCom Symbols/
  OCHA Humanitarian Icons/
```

### Important import behavior

- Each imported image gets an embedding immediately.
- In the current repository configuration, the embedding provider auto-configuration expects AWS Bedrock credentials.
- If embedding generation fails, the image import is rejected and the file is cleaned up.
- If no description is supplied, EasyRead derives one from the filename.

You must provide your own credentials and assets before running the application:

## Troubleshooting

### `type "vector" does not exist`

Your database is missing the `pgvector` extension. Connect to the target database and run:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

### Frontend loads, but requests fail

Check that:

- Django is running on the port in `DJANGO_PORT`
- `VITE_API_BASE_URL` and `VITE_MEDIA_BASE_URL` point to that same backend
- You restarted the frontend after changing `.env`

### `Failed to load image sets`

Make sure:

- the backend is reachable at `/api/image-sets/`
- the database has imported image sets
- any reverse proxy in front of Django is not forwarding unrelated Basic Auth credentials to the backend API

### PDF upload reports no converter response

The frontend supports either:

- the built-in local `/api/pdf-to-markdown/` endpoint, or
- an external converter controlled by `VITE_USE_EXTERNAL_PDF_CONVERTER`

If you are running locally, make sure the frontend is pointing at the backend you actually started.

### Long-running model calls time out

For Bedrock-backed flows you can tune:

- `AWS_BEDROCK_CONNECT_TIMEOUT`
- `AWS_BEDROCK_READ_TIMEOUT`
- `AWS_BEDROCK_MAX_ATTEMPTS`
